# ТЗ: длинные тексты, полные ответы, индикация прогресса

## 0. Контекст

Сервис Triple-Pass Text Reviewer (три независимых LLM-прогона + консенсус)
работает, но три жалобы от пользователя:

1. **Не тянет длинные тексты** — на длинном вводе прогоны обрезаются или
   падают, часть замечаний теряется.
2. **Скомканные ответы** — отчёт куцый, замечания слишком короткие, мало
   конкретики.
3. **Нет обратной связи в UI** — после нажатия «Проверить» пользователь
   видит зависший индикатор и тишину до готового отчёта (30–90 секунд).

Задача — устранить все три, не меняя концепцию «три прогона + консенсус
2-из-3» и не ломая существующие тесты. Целевой пользователь — редактор,
вставляющий русский текст в браузере (Gradio на HF Spaces, провайдер по
умолчанию Groq / Llama-3.3-70b).

## 2. Задача / проблемы, которые надо решить

### 2.1. Обработка длинных текстов (обрезка/падение вывода)

**В чём проблема сейчас.** `orchestrator._run_pass` вызывает
`client.call(system=system, user=user_msg)` без указания `max_tokens`, то
есть с дефолтом `4096` (`base.py`). Модель выдаёт человекочитаемый отчёт, а
затем обязательный JSON-блок. На длинном тексте суммарный вывод упирается в
4096 токенов, JSON обрезается → `parse_pass` бросает `ParseError` → ретрай
«верни только JSON» тоже ограничен 4096 → на очень длинном тексте прогон
падает в `failed`. Вход (20000 символов) в контекст модели помещается —
узкое место именно на **выводе**.

**Требование.**

1. **Сквозной параметр бюджета вывода.**
   - Добавить env `LLM_MAX_TOKENS` (int, дефолт `8000`). Читать в
     `orchestrator.py` при старте: `MAX_OUTPUT_TOKENS = int(os.environ.get(
     "LLM_MAX_TOKENS", "8000"))`.
   - Все вызовы `client.call(...)` внутри `_run_pass` (первичный, JSON-ретрай,
     nudge-ретрай) должны передавать `max_tokens=MAX_OUTPUT_TOKENS`.
   - Дефолт `8000` подобран так, чтобы полный отчёт с JSON на тексте ~20000
     символов помещался без обрезки на Llama-3.3-70b (у Groq потолок
     вывода для этой модели — 32768, так что 8000 безопасно). Пользователь
     может поднять/опустить через env.

2. **Детект обрезки вывода.**
   - Расширить `LLMResponse` в `providers/base.py` полем
     `truncated: bool = False` (dataclass, значение по умолчанию —
     обратная совместимость сохраняется).
   - В `_openai_compat.py` выставлять `truncated=True`, если
     `resp.choices[0].finish_reason == "length"`. Для остальных провайдеров
     (`anthropic.py`, `gemini.py`) — по возможности аналогично
     (`stop_reason == "max_tokens"` у Anthropic; у Gemini —
     `finish_reason`/`MAX_TOKENS`). Если у провайдера сигнала нет — оставить
     `truncated=False`, это допустимо.
   - В `_run_pass`: если после всех ретраев прогон всё равно не распарсился
     ИЛИ последний ответ пришёл с `truncated=True`, добавить в
     `PassResult.failure_reason` / warnings человекочитаемую пометку, что
     текст, возможно, слишком длинный для одного прогона.

3. **Понятное предупреждение в отчёте.** В `orchestrator.review` при сборке
   `warnings` для прогона, чей ответ был обрезан по длине, добавить строку
   (на английском, как остальные warnings — их переводит `_translate_warning`
   в `app.py`), например: `Pass {pid} truncated: output hit the token limit,
   some findings may be missing`. В `app.py._translate_warning` добавить
   разбор этого паттерна в русский текст вида: «{Прогон}: ответ модели
   обрезан по лимиту длины — часть замечаний могла потеряться. Уменьшите
   объём текста или поднимите `LLM_MAX_TOKENS`.»

4. **Чанкинг НЕ реализуем** (см. раздел 4 «Риски»). Вход остаётся цельным:
   `number_text` нумерует весь текст, каждый прогон видит его целиком. Это
   принципиально для прогона 2 (поиск противоречий между удалёнными
   абзацами) — разбивка на чанки его сломала бы.

5. **Лимит длины входа.** `MAX_TEXT_CHARS` (дефолт 20000) оставить
   настраиваемым через env. Сообщение при превышении в `app.py` уже
   понятное — не трогать. По умолчанию не поднимать (см. «Риски» про
   стоимость и rate-limit).

**Крайние случаи.**
- Пустой текст — уже обрабатывается в `review_text` (не трогать).
- Один прогон обрезан/упал, два других ок — консенсус строится по рабочим,
  отчёт отдаётся с предупреждением (текущее поведение `build_consensus`
  корректно, `failed` прогоны исключаются). Проверить, что не падает.
- Все три прогона упали — отчёт с пустым консенсусом и тремя
  предупреждениями. Не должно быть исключения.

### 2.2. Полные, не скомканные ответы

**В чём проблема сейчас.** Два фактора:
1. Обрезка по `max_tokens` (решается в 2.1).
2. UI-отчёт (`app.py._fmt_report`) собирается **только** из структурированных
   `findings` (`quote` / `defect` / `fix`). Человекочитаемая проза, которую
   модель пишет перед JSON, лежит в `PassResult.raw_response` и **никак не
   рендерится**. При этом промты требуют от `defect`/`fix` «одну-две фразы»,
   поэтому замечания выходят телеграфными.

**Требование.** Повысить содержательность **внутри JSON-контракта**, не
меняя схему `Finding`, ключи `PASSES` и `ALLOWED_CATEGORIES`:

1. **Промты (`passes.py`).** В каждом из трёх системных промтов смягчить
   требование к длине полей `defect`/`fix`:
   - Для `defect` (в разных промтах называется «В чём ошибка / проблема /
     что произошло при чтении»): заменить «одна-две фразы» на требование
     «2–4 полных предложения: что именно не так, какое правило/ожидание
     нарушено, и почему это важно для читателя. Без воды, но с конкретикой».
   - Для `fix` (в разных промтах — «Как исправить / что помогло бы читателю»):
     потребовать конкретный переписанный вариант фрагмента (а не абстрактный
     совет), допустимо до трёх альтернатив. Формулировка: «Дай конкретную
     замену — как должно быть написано, дословно. Абстрактные советы ("сделай
     понятнее") не принимаются».
   - НЕ трогать: список категорий, разрешённые категории прогона, требования
     к дословности цитаты, блок `_OUTPUT_CONTRACT` (JSON-схему).
   - Бумпнуть `PASS_VERSION` на новую дату (формат `YYYY-MM-DD`, текущая
     дата реализации). Это нормально — версия для того и есть. НЕ удалять
     константу и не менять её имя.

2. **Рендер (`app.py._fmt_report` и `src/reviewer/report.py`).** Убедиться,
   что многострочные `defect`/`fix` рендерятся полностью. Сейчас `_fmt_finding`
   выводит каждый элемент `it.defects` / `it.fixes` одним `- {...}` пунктом.
   Требование: если значение содержит переносы строк — не ломать разметку
   (заменять внутренние `\n` на пробел ИЛИ рендерить как есть, но без
   поломки Markdown-списка). Прочий формат отчёта не менять.

3. **Опциональный «развёрнутый разбор».** В `app.py` под итоговым отчётом
   добавить сворачиваемый блок (`gr.Accordion`, свёрнут по умолчанию)
   «Полные ответы прогонов», показывающий `raw_response` каждого прогона
   как есть. Это даёт редактору доступ к человекочитаемой прозе модели,
   которую сейчас выбрасывают. Реализовать через дополнительный
   `gr.Markdown`/`gr.Textbox` внутри аккордеона, заполняемый из
   `report.passes[*].raw_response`. Не обязателен для консенсуса — чисто
   для прозрачности.

**Крайние случаи.**
- `defect`/`fix` пришли всё равно короткими (модель не послушалась) —
  это не ошибка приёмки, промт лишь усиливает вероятность. Тестируем
  контракт, не поведение живой модели.
- `raw_response` пустой (прогон упал) — в аккордеоне показать «Прогон
  не дал ответа».

### 2.3. Индикация прогресса в UI

**В чём проблема сейчас.** `review_text` в `app.py` вызывает
`progress(0.1, desc=...)`, затем блокирующий `asyncio.run(run_review(...))`,
затем `progress(1.0)`. Между 0.1 и 1.0 обновлений нет — `review` внутри
делает `asyncio.gather` и отдаёт результат только когда готовы все три
прогона. Пользователь видит зависший бар.

**Требование.**

1. **Колбэк прогресса в оркестраторе.** Добавить в `review()`
   необязательный параметр `on_progress: Callable[[int, int, str], None] |
   None = None` (аргументы: `done`, `total`, `pass_id`). Существующая
   сигнатура остаётся совместимой — тесты зовут `review(SOURCE, "tid",
   client=client)` без него.
2. **Пер-прогонное обновление.** Заменить `asyncio.gather` на
   `asyncio.as_completed` (или `asyncio.wait` с `FIRST_COMPLETED`), чтобы
   вызывать `on_progress(done, 3, pass_id)` по мере завершения каждого из
   трёх прогонов. Порядок результатов в итоге всё равно сортируется по
   `pass_id` (как сейчас, `results.sort`) — рандомизация запуска
   (`random.shuffle`) сохраняется.
3. **Проброс в Gradio.** В `app.py.review_text`:
   - Перед запуском: `progress(0.05, desc="Готовлю текст…")`.
   - Передать в `run_review` колбэк, который маппит `done` в долю
     `0.1 + 0.8 * done/3` и пишет `desc=f"Готов прогон {done} из 3…"`.
     Колбэк вызывается из корутины в том же worker-потоке Gradio (т.к.
     `asyncio.run` исполняется в этом потоке), поэтому прямой вызов
     `progress(...)` из колбэка безопасен.
   - После сборки отчёта: `progress(1.0, desc="Готово")`.
   - Подписи прогонов брать из уже существующего `PASS_LABELS` / `PASS_SHORT`,
     чтобы в статусе было понятно, какой прогон завершился (например
     «Готов: Прогон 2 · Логик-придира (2 из 3)»).
4. **Queue.** `demo.queue()` уже включён в `__main__` — прогресс через
   `gr.Progress` работает только с очередью, ничего дополнительно включать
   не надо, но проверить, что `.click(review_text, ...)` не отключает queue.

**Крайние случаи.**
- Прогон упал — колбэк всё равно вызывается (as_completed завершает и
  упавшую задачу), `done` инкрементируется. Индикатор не зависает.
- Rate-limit / пустой текст / нет ключа — ранний выход до запуска прогонов,
  как сейчас; прогресс-бар просто не стартует.

## 4. Риски и цена

- **Стоимость вывода.** Поднятие `max_tokens` с 4096 до 8000 увеличивает
  максимальный объём вывода вдвое, на трёх прогонах — до ~24k выходных
  токенов на проверку в худшем случае. На **Groq (free)** — бесплатно, но
  есть лимиты TPM/RPM: три параллельных вызова по 8k вывода на длинном
  тексте могут упереться в rate-limit провайдера → сработает фолбэк или
  прогон упадёт. На платных провайдерах (OpenAI/Anthropic) выходные токены
  дороже входных в 3–5 раз — считать по факту, но при текстах ~20k символов
  это всё равно центы за проверку.
- **Стоимость входа при раздувании `MAX_TEXT_CHARS`.** Нумерация
  (`number_text`) добавляет маркеры `[Paragraph N]` и `[N.M]` — вход растёт
  на ~30–50% в токенах. При 20000 символов это ~8–12k входных токенов ×3
  прогона. Если кто-то поднимет `MAX_TEXT_CHARS` до 50k+ и подключит крупную
  платную модель — стоимость и латентность растут линейно. Поэтому дефолт
  `MAX_TEXT_CHARS` не поднимаем, а в README отмечаем, что это плата за токены.
- **Отвергнутая альтернатива — чанкинг.** Разбивка длинного текста на куски
  ломает прогон 2 (поиск противоречий между далёкими абзацами: разные куски
  — разные вызовы, модель не видит их вместе), усложняет сквозную нумерацию
  абзацев и умножает число вызовов (=стоимость и rate-limit). При этом
  реальное узкое место — **вывод**, а не вход, и оно чинится поднятием
  `max_tokens` без чанкинга. Поэтому чанкинг не делаем; при потребности в
  реально гигантских текстах — это отдельная большая задача с деградацией
  качества, обсуждать отдельно.
- **Латентность прогресса.** Пер-прогонная индикация показывает шаги, но
  сами прогоны идут параллельно и завершаются близко по времени — бар может
  прыгнуть с ~10% до 90% почти сразу, если все три ответят одновременно.
  Это приемлемо: главное — что бар живой и есть статус, а не мнимая
  плавность.
