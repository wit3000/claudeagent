# Как писать ТЗ

ТЗ пишется в файл `specs/<краткое-имя>.md`. Имя — короткое и по сути
(`deploy-hf`, `provider-switch`). ТЗ считается готовым, только если кодер
может реализовать всё по пунктам, не задавая вопросов.

## Принципы

1. **Сверяйся с кодом, не выдумывай.** Прежде чем писать «что уже есть»,
   прочитай реальные файлы (README, SPEC, src/). Любое утверждение о текущем
   поведении должно быть проверяемо.
2. **Конкретика вместо намерений.** Не «улучшить деплой», а «создать
   `scripts/deploy_hf.py`, который принимает `--space` и делает X, Y, Z».
   Указывай конкретные файлы, функции, интерфейсы, имена переменных.
3. **Явно фиксируй, что нельзя ломать.** Существующие тесты, публичные
   контракты, поведение фронта.
4. **Крайние случаи и ошибки — часть ТЗ.** Что делать при пустом вводе,
   сетевом сбое, нарушенном формате ответа, превышении лимита.
5. **Критерии приёмки проверяемы.** Каждый пункт можно однозначно отметить
   как «сделано / не сделано».
6. **Честная оценка цены.** Если решение дорогое (платные API, тяжёлый
   хостинг) или рискованное — скажи об этом в разделе «Риски» и предложи
   более дешёвую альтернативу. Лучше отговорить, чем написать плохое ТЗ.

## Шаблон

Скопируй структуру ниже в новый файл `specs/<имя>.md` и заполни.

```markdown
# ТЗ: <название задачи>

## 0. Контекст
Зачем это нужно, для какого пользователя, какую проблему решаем.
Кратко — но достаточно, чтобы кодер понял смысл, а не только механику.

## 1. Что уже работает (не ломать)
Список текущего рабочего поведения и файлов, которые нельзя сломать.
Ссылки на конкретные модули и тесты.

## 2. Задача / проблемы, которые надо решить
Для каждой проблемы — отдельный подраздел:
### 2.x. <короткое имя проблемы>
- В чём проблема сейчас.
- **Требование:** что конкретно должно появиться/измениться (файлы,
  функции, интерфейсы, поведение, env-переменные).
- Крайние случаи и обработка ошибок.

## 3. Ограничения и зависимости
Версии, окружение, лимиты, внешние сервисы, обратная совместимость.

## 4. Риски и цена
Сложность, время, деньги. Что может пойти не так. Альтернативы, если
основной путь дорогой или рискованный.

## 5. Критерии приёмки
Проверяемый чек-лист. Каждый пункт — «сделано / не сделано».
- [ ] ...
- [ ] ...

## 6. Тесты
Какие тесты добавить/обновить, какие команды прогнать (например
`pytest -q`), что считать зелёным прогоном.
```

Эталон стиля и уровня детализации — файл `SPEC.md` в корне репозитория.
Ориентируйся на него.
